Approach
Structured thinking
in messy conditions.

Every real project starts as a mess — vague requirements, competing priorities, unclear scope. My job is to find the structure inside the chaos and build toward it.

Not by following a textbook process. By staying disciplined about what matters and moving fast on everything else.

01

Read everything before touching code

Client requirements, vague briefs, stakeholder notes. I map the domain and the real constraints before a single schema gets designed. Most "technical" problems are scope problems in disguise.

→ domain mapping first
02

Schema before wireframe

The data model is the architecture. I design all entities and relationships before any interface decision. The database shape determines everything downstream.

→ structure before interface
03

Cut to the smallest real thing

V1 is not the vision. It's the minimum that proves the concept with real data, real auth, real workflows. Everything else is sequenced — not dropped.

→ scope ruthlessly
04

Build in the right order

Auth → data layer → API contracts → frontend consuming real endpoints. No mocked data in production code. No UI before the backend is real.

→ foundation before feature
05

Ship. Then learn. Then fix.

Deployed software teaches you things no prototype can. The first deployment is where real feedback starts — not the finish line.

→ ship then iterate

AI control

I control the AI.
Not the other way.

AI amplifies both good thinking and bad thinking. In a messy project, it generates confident-sounding nonsense if you let it run without constraints.

My workflow uses AI as a thinking partner under strict rules — not as an output machine. Every decision that ships is mine to own.

Stage 01

Frame the problem first, AI second

I describe the messy brief in full before asking AI anything. Vague input produces confident garbage. Precision in the prompt is precision in the output.

Stage 02

Options, not answers

I ask for three different approaches to a problem, then evaluate trade-offs myself. AI gives breadth. I provide judgment. The decision is always mine.

Critical checkpoint

Schema design stays human

I never let AI design the data model. The database schema is the most load-bearing decision in any project. I own it completely. AI doesn't touch it.

Stage 03

Debug by explaining, not by pasting

When I'm stuck, I describe the bug to AI in full. Articulating the problem clearly usually reveals it. AI is a thinking mirror — not a fix machine.

Stage 04

Refactor after it works

I get the feature working with my own logic first. Then I ask AI to review for patterns and readability. Never the reverse — functionality is not negotiable.

Always

Read every line before it ships

If AI suggests a change, I read it line by line and understand it before it enters the codebase. I don't ship code I can't explain.
